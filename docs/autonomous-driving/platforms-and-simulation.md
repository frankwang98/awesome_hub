# 自动驾驶平台、仿真与迁移策略

> 旧 Wiki 中的 Apollo、Autoware、CARLA 与 ROS1 笔记，统一收敛为平台理解与迁移策略，而不是绑定某个过期版本的安装教程。

## 平台不是架构本身

Apollo、Autoware、ROS 生态和自研 Runtime 都可以提供感知、定位、规划、控制、车辆接口、监控和工具链。但项目应先定义自己的领域边界：

```text
任务 / 路由 / 车辆状态 / 障碍物
                ↓
行为决策 → 规划 → 控制 → 安全仲裁
                ↓
      ROS / 仿真器 / 实车适配层
```

平台负责提供组件、协议与工具；核心业务规则、场景差异和安全策略不应完全依附于某个开源平台的内部目录结构。

## Apollo 与 Autoware 的学习方式

| 关注点 | 建议 |
| --- | --- |
| 系统全景 | 先梳理感知、定位、规划、控制、车辆接口、监控与数据回放的输入输出。 |
| 源码阅读 | 从一个闭环场景开始追踪消息：定位 → 规划 → 控制 → 底盘。 |
| 二次开发 | 优先通过明确接口、配置与独立包扩展，不直接散改大仓库核心逻辑。 |
| 笔记沉淀 | 记录模块边界、运行时数据流、调试方式和版本差异，而不只记录安装命令。 |

## 仿真选择

| 工具 | 更适合验证什么 |
| --- | --- |
| Gazebo | 机器人模型、传感器、ROS2 节点与物理交互。 |
| CARLA | 道路场景、交通参与者、相机/雷达数据与自动驾驶评测。 |
| RViz / rosbag | 可视化、接口检查与可重复回放。 |
| 实车 / HIL | 延迟、标定、故障与安全降级的最终验证。 |

## 从 ROS1 旧项目迁移时

- 不把 ROS1 的 package、launch 和 topic 命名机械翻译到 ROS2。
- 先抽出可测试的 C++ 领域逻辑，再分别实现 ROS1 / ROS2 adapter。
- 重新设计 QoS、生命周期、参数、时间同步和安全超时处理。
- 用场景测试和 rosbag 回放校验迁移前后的轨迹、控制和故障行为。

## 与 ROS2Drive 的关系

`ROS2Drive` 可作为个人项目的参考 Runtime：场景通过配置接入，领域层不依赖 ROS，安全层拥有最终命令仲裁权。学习 Apollo、Autoware 与仿真器时，优先把所得结论回填到这一类稳定接口中。
