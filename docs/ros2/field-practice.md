# ROS2 工程实践：通信、传感器与仿真

> 从旧 Wiki 的 ROS1、DDS、传感器、PCL 与仿真笔记中提炼。目标不是复刻某个历史环境，而是建立可迁移到 ROS2 的工程检查表。

## 通信边界

ROS2 的节点负责适配和编排；领域逻辑应可以脱离 ROS 单独运行和测试。

```text
domain / planning / control
             ↑↓
     ROS adapter layer
             ↑↓
topics · services · actions · parameters · QoS
```

- **Topic**：持续状态流，如传感器、定位、轨迹与控制指令。
- **Service**：短请求/响应，如读取一次配置或触发轻量操作。
- **Action**：有进度、可取消的任务，如导航、泊车、地图加载。
- **Parameter**：启动配置，不应用作高频运行时数据通道。

## DDS / QoS 检查表

ROS2 基于 DDS，但通常无需直接操作 DDS API。需要主动设计的是 QoS：

| 数据类型 | 常见取舍 |
| --- | --- |
| 控制指令、急停 | 优先低延迟；明确丢包和超时后的安全降级。 |
| 地图、配置、静态模型 | `transient_local` 适合让后启动节点获取最后一份数据。 |
| 传感器流 | 根据带宽选择 `best_effort` 或 `reliable`，不要默认可靠传输。 |
| 任务状态、事件 | 需要可追溯时使用可靠传输，并定义队列深度。 |

所有跨节点接口都应写清消息频率、时间戳来源、坐标系、QoS 和失效行为。

## 多传感器时间同步

- 先统一时钟和时间戳语义，再讨论 `message_filters`。
- `ExactTime` 只适用于严格同源、同频的时间戳；多数实车传感器应优先评估 `ApproximateTime`。
- 同步窗口、队列长度和最大延迟必须按传感器频率和实际链路测量设置。
- 记录未匹配、超时、乱序与丢帧指标；时间同步失败不能悄悄产生“看似正常”的融合结果。

## 传感器、坐标与点云

1. 先确定 `base_link`、传感器坐标系、地图坐标系和 TF 发布者的唯一性。
2. 相机、雷达、IMU、GNSS 驱动只负责采集与原始消息；标定、同步、融合放在独立节点。
3. 使用 `cv_bridge`、`pcl_conversions` 等适配层时，明确拷贝成本与时间戳是否保留。
4. RViz 是诊断工具，不是系统事实来源；关键状态应有日志和可回放数据。

## 仿真与真实系统

- Gazebo / CARLA 适合验证接口、场景和故障注入；不要将仿真话题名称直接写死在领域逻辑中。
- 真实车辆接口应隐藏在 adapter 内，统一输出车辆状态并统一接收安全约束后的控制命令。
- 每个场景至少覆盖：正常运行、定位失效、传感器超时、规划失败、急停与恢复。
